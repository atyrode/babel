# Sandbox threat model

Status: backend selection and this threat model are settled 2026-08-30 (§13 decisions 57–59), and the Linux backend is implemented in Code with its escape scenarios exercised against the real mechanisms — six scenarios covering filesystem, egress, task-count, memory, teardown and reaping, each proven non-vacuous by relaxing the control it tests, plus a prerequisite guard that fails loudly rather than letting the scenarios skip into a green suite. So §10's "live containment/escape scenario in every enabled sandbox backend" is satisfied for the one enabled backend, which is what qualifies Linux for analysis. What is **not** done, and remains issue #75: a real configured-profile exploration against a live provider, a harmless repository experiment, brokered public-research retrieval, and a critical challenger changing or preserving a conclusion. Phase B is not accepted; the boundary it will run behind is tested.

This document exists so that a reviewer holding a run receipt can check the boundary it declares against a written one. SPEC.md §14's first Phase B gate points here. Section 8 names the changes that make this document wrong; whoever makes one of them updates it in the same change.

## 1. What is being contained, and why

The analysis worker is OMP running a model over the operator's own archived conversations, with `bash`, `edit`, `write` and `browser` in its tool set. Each of those is a host-effect tool: `bash` executes arbitrary commands, `edit` and `write` mutate the filesystem, and `browser` executes arbitrary JavaScript with process-level access.

The worker is headless, and OMP states the consequence for confirmation directly: "`tools.approvalMode` is forced to `yolo` because headless subagents have no UI to confirm prompts against" (`omp://tools/task.md`). Interactive approval is therefore not one of the controls and cannot be made one by configuration — there is no surface to confirm against. This is not a misconfiguration to fix; it is what headless means.

That leaves exactly two controls between the model and the host. Babel authorizes every tool request against the run's grant and denies a capability the grant never included (§2.6, decision 53). The operating system contains what the worker's own process tree does. These cover different things and neither substitutes for the other: Babel's authorization is a control-plane check over the requests the worker routes through Babel, and a `bash` command the model issues locally never reaches Babel at all. The OS boundary is the only control that covers the local case, which is why it has to be real.

The corpus is what makes the consequence concrete. The worker reads the operator's complete archived conversation history across three harnesses, which §3 already classifies: "All archive content is untrusted data. A transcript can contain malicious instructions copied from issues, web pages, repositories, tool output, or prior agents." So the boundary is not only containment for a hypothetically malicious model. It is containment for an ordinary, cooperative model that read attacker-authored text in the corpus and then acted with the tools above — the more likely of the two failures, and the one no amount of model quality removes.

## 2. Why Babel does not implement it

Decision 53, recorded 2026-08-29 and not re-argued here: Code owns the disposable sandbox and credential isolation because Code owns the profile, the provider credential and the OMP controller, and a second sandbox in Babel would duplicate the boundary while splitting responsibility for it. Babel's half is grant authorization and process-tree lifetime. What follows describes the backend Code implements and, exactly, which properties Babel's `Containment` declaration may honestly assert about it.

## 3. Why OMP cannot supply it

OMP is the contained program, not the container. Its own documentation says so at every surface that could be mistaken for a boundary:

- In-process extension code: "Extensions are **not sandboxed** (same process/runtime)" (`omp://extension-loading.md`). An extension is therefore not a place to enforce policy against the agent it extends — it runs with that agent's authority.
- "`run` code has full Node/Bun and session-tool access; it is not sandboxed" (`omp://tools/browser.md`).
- "`code` has full host access and is not sandboxed" (`omp://tools/computer.md`).

The one OMP mechanism that resembles isolation is `pi-iso`, the workspace backend behind `isolated: true` subagents: "Isolation backend implementations and diffing for APFS, Linux/Windows clone/reflink paths, overlayfs, ProjFS, and recursive copy fallback" (`omp://native-crates.md`). The word *diffing* is the tell. `pi-iso` gives a subagent a copy-on-write view of the workspace so its changes can be captured as a patch or a branch, and its documented degradation is falling back through candidate backends to "recursive copy as last resort" (`omp://tools/task.md`). A security boundary does not degrade to a recursive copy. It is a correctness mechanism for capturing diffs: it changes where workspace writes land, and nothing about the process making them, so `bash`, the network, and every path outside the workspace stay exactly as reachable as before.

OMP states its own assumption in the file-write fallback seam, which exists precisely for hosts that do sandbox it: "Intended for a host that embeds the agent inside a sandbox denying direct filesystem writes but exposing a privileged write channel" (`omp://extensions.md`). OMP expects its host to provide the sandbox. Code is that host, and this document is that sandbox.

## 4. The Linux backend

`bwrap --unshare-all --die-with-parent` executing inside a `systemd-run --user --scope`. Two mechanisms, because neither covers both halves: bubblewrap provides namespace and filesystem isolation and no resource accounting whatsoever, while a transient systemd scope provides cgroup v2 ceilings and no isolation whatsoever. Composed, they establish the four properties the wire contract requires; separately, each would force a declaration with a false boolean in it.

### 4.1 Mechanism per declared property

| Declared property | Mechanism that establishes it |
| --- | --- |
| `backend: "bwrap+systemd-scope"` | Names both halves, because a receipt naming only one would describe a boundary that does not exist. |
| `filesystem_isolation: true` | bubblewrap's mount namespace. The sandbox sees a filesystem Code constructs mount by mount — read-only binds for the runtime, a private `/proc` and `/dev`, tmpfs for writable scratch — rather than the host tree with paths denied. What is not mounted does not exist inside, so the failure mode of forgetting a rule is absence rather than exposure. |
| `network_default_deny: true` | bubblewrap's network namespace (`--unshare-all` includes `--unshare-net`). The sandbox holds one interface, its own loopback, and no route to anything. Denial is the absence of a path, not a filter that could be misordered. Section 5 covers the single permitted egress and what it leaves reachable. |
| `resource_ceilings: true` | The transient systemd scope's cgroup v2 limits: `MemoryMax`, `CPUQuota`, `TasksMax`. Section 4.4 states precisely which ceilings this covers and which it does not, because the boolean is coarser than the mechanism. |
| `disposable: true` | `--die-with-parent` plus the scope. The sandbox's writable state is tmpfs that ceases to exist with the mount namespace, and `--die-with-parent` "Kills with SIGKILL child process (COMMAND) when bwrap or bwrap's parent dies" (`bwrap --help`, 0.11.2), so the tree dies with Code rather than surviving it. This composes with Babel's own process-tree lifetime ownership (decision 53) rather than replacing it: Babel reaps grandchildren from outside, and `--die-with-parent` covers the case where Babel's reaping never runs because the parent was killed uncatchably. |
| `escape` | Section 6, in the same words Code declares. |

### 4.2 Mechanism measurements

Measured 2026-08-30 on the operator's primary Linux workstation — Linux 6.8.0-136-generic, bubblewrap 0.11.2, systemd 261 (261.1), `kernel.unprivileged_userns_clone=1`, `user.max_user_namespaces=62308`. **These measure the mechanisms in isolation.** They are what justified the selection before the backend existed; the backend that composes them is now implemented and carries its own escape scenarios, which assert the same properties through Code's real launch path rather than through hand-run commands. Both layers are kept: these readings say the mechanism works on this host, the scenarios say Code uses it correctly, and a regression in either is a different bug. No exploration run against a live provider has executed behind this backend (issue #75).

- **No interface but loopback.** Inside `bwrap --ro-bind / / --dev /dev --proc /proc --unshare-all --die-with-parent`, `/proc/net/dev` lists exactly one device, `lo`.
- **No route out.** An outbound TCP connect to a public address from inside that sandbox fails with `Network is unreachable`; the identical connect from the host in the same shell succeeds. Egress denial is observed, not inferred from flag documentation.
- **A bind-mounted unix socket crosses the boundary.** With `--bind <dir> /run/egress` added, a process inside the network namespace connected to a host-side `AF_UNIX` listener in that directory and read its reply. Filesystem-bound unix sockets are not governed by the network namespace, which is what makes Section 5's design possible without giving the sandbox an interface.
- **Ceilings apply.** `systemd-run --user --scope -p MemoryMax=256M -p CPUQuota=50% -p TasksMax=64` produced a scope under `user@1000.service/app.slice` whose `memory.max` read `268435456`, `cpu.max` read `50000 100000`, and `pids.max` read `64`.
- **No IO ceiling is available.** The same scope had no `io.max` file. `cgroup.controllers` at the delegation point is `cpu memory pids`; `io`, `cpuset`, `hugetlb`, `rdma` and `misc` are enabled at the cgroup root but not below `user.slice`. See Section 4.4.
- **Ceilings cannot be raised from inside.** In the composed arrangement the sandbox's cgroup namespace is unshared (`/proc/self/cgroup` reads `0::/`, so the scope's path is not even visible), `/sys/fs/cgroup` is read-only, and a write to the slice's `memory.max` failed with `Read-only file system`. Effective capabilities inside were `0000000000000000` — bwrap runs here as a non-setuid binary relying on unprivileged user namespaces, and the sandboxed process holds no capability in any namespace.
- **Teardown is uncatchable.** A parent holding a `--die-with-parent` sandbox was `SIGKILL`ed; the three processes matching the sandboxed command before the kill were all gone afterwards. `SIGKILL` on the parent is the case an exit handler cannot cover, which is why disposability does not rest on one.

### 4.3 Prerequisites, and what happens when each is absent

Three host properties are load-bearing. Each has a distinct absence behavior, and in every case the correct behavior is a refused run rather than a run behind a weaker boundary — because a run that proceeds has to declare something, and the only thing it could honestly declare is less than the requirement.

- **Unprivileged user namespaces.** `bwrap` here is not setuid; it creates its namespaces as the invoking user. Where a kernel or distribution policy forbids that — `kernel.unprivileged_userns_clone=0`, `user.max_user_namespaces=0`, or an AppArmor/LSM policy denying `userns_create` — `bwrap` fails to start. Nothing degrades: there is no sandbox, so there is no declaration to make, and Code must refuse rather than run OMP unwrapped.
- **cgroup v2 controllers delegated to the user slice.** Without `memory` and `pids` available at the point where a `--user` scope lands, the scope starts and the limits silently do not apply — this is the one prerequisite whose absence is quiet, which makes it the one that must be checked rather than assumed. `resource_ceilings: true` is only honest if the limits are observed in the created scope's cgroup files, not merely requested on the command line.
- **A user D-Bus session for the transient scope.** `systemd-run --user` needs the user manager's bus. Measured 2026-08-30: with `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR` both unset it fails with `Failed to connect to user scope bus via local transport: $DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined`. This is the realistic absence, not an exotic one: it is the state of a bare `ssh` command, a cron job, or a system service context. A worker launched from such a context has no resource ceilings, so it cannot declare them.

### 4.4 What `resource_ceilings: true` covers, and what it does not

The wire contract has one boolean and the mechanism has a controller set, so the boolean is coarser than the truth and the difference belongs here rather than in a footnote. `resource_ceilings: true` under this backend means an enforced ceiling on four dimensions: **resident memory** (`MemoryMax`, with swap denied), **CPU share** (`CPUQuota`), **process and thread count** (`TasksMax`), and **the space each writable mount can hold**.

That last one does not come from the scope at all. Every writable mount inside the sandbox is a `tmpfs` created with an explicit size, so disk space is bounded by the mount rather than by a controller — measured 2026-08-30, `bwrap --size 1048576 --tmpfs /tmp` caps it, and `dd` of 4 MiB into that 1 MiB mount exits 1. Note the argument order: `--size` must precede the `--tmpfs` it applies to, and the reverse is an error rather than a silently unbounded mount. Because `tmpfs` pages are charged to the cgroup that touches them, the same bytes are also bounded by `MemoryMax` — disk space is bounded twice, by different mechanisms, which is why exhausting it cannot become a way to exhaust the host.

What `resource_ceilings: true` does **not** mean is an IO-*bandwidth* ceiling. Measured 2026-08-30, `io` is not among the controllers enabled below `user.slice` on the operator's own workstation, so a user scope has nothing for `IOMax`/`IOWeight` to act on. A worker cannot exhaust memory, monopolize the CPU, fork without bound, or fill a disk; it can saturate the disk it reads the corpus from.

**The trap that makes this worth a section.** `systemd-run --user` **accepts** `IOReadBandwidthMax` with exit status 0 and then silently drops it: measured 2026-08-30, the requested property produced a scope whose cgroup had no `io.max` file at all. Exit status is not evidence of enforcement here. So a future reader must not add an IO property and assume it took effect — the only way to know a ceiling exists is to read it back out of the created scope's cgroup, which is what this backend does before it declares anything. Delegating `io` into the user manager's slice would need a system-level change outside Babel and outside the operator's per-user reach, which is why the gap is recorded rather than closed.

The same read-back discipline resolves the quiet prerequisite in Section 4.3, and it is not symmetrical: `cpu` is absent from a bare scope's `cgroup.controllers` and appears when `CPUQuota` is actually requested, because systemd enables the controller it needs. So "the controller was missing a moment ago" is not evidence either. Only the created scope's own cgroup files are.

That is recorded rather than smoothed over because a reviewer reading `resource_ceilings: true` will otherwise read a stronger claim than the mechanism delivers. The boolean stays `true` because the four ceilings it does carry are the ones that bound a runaway analysis worker into a survivable failure; the IO gap is a denial-of-service surface against the operator's own machine, not a containment hole.

## 5. The egress design

The sandbox has no network. Egress exists only as host-side sockets bind-mounted into it: an HTTP `CONNECT` proxy owned by Code, allowlisting only the resolved provider endpoint the run's profile names, and — where the run's auth broker is a service on this same host — a second relay for it.

Three parts, then the broker:

1. **The proxy is host-side and Code's.** It runs outside the sandbox, in Code's own process tree. It accepts `CONNECT host:port` and refuses every target that is not the resolved provider endpoint. Because it is outside, the sandbox cannot reconfigure it, restart it with a wider allowlist, or read its policy — the allowlist is not data the contained program can reach.
2. **The channel is a bind-mounted unix socket.** Measured in Section 4.2: an `AF_UNIX` socket on a bind-mounted path is reachable from inside the network namespace. This is what lets egress exist without the sandbox holding an interface. The sandbox gets one file descriptor's worth of reachability into one host process, rather than a route.
3. **An in-sandbox forwarder makes OMP's documented hook work unmodified.** OMP's documented proxy hooks are environment variables carrying a proxy URL (`omp://environment-variables.md`), and no unix-socket proxy scheme appears among them; a socket path is therefore not something the documented surface accepts. A small forwarder inside the sandbox listens on the sandbox's private loopback, relays each accepted connection to the bind-mounted socket, and `PI_PROXY` points at it. Nothing in OMP is patched, and no undocumented OMP behavior is relied on.

4. **A second socket relays the auth broker, when the broker is local.** Discovered while implementing this backend rather than while designing it, and it is load-bearing: Code resolves the provider credential through an auth broker, and on the operator's own machine that broker is a **loopback** service. Both halves of the design above defeat reaching it. OMP never sends a loopback target through a proxy — "Loopback, link-local, private-range … targets always bypass" — and the sandbox's loopback is its own, so the host's broker is not there. A run would authenticate against nothing.

   So a second unix socket is bind-mounted in, a second in-sandbox forwarder listens on the sandbox's loopback, and the child's broker URL is rewritten to point at it. A broker that is *not* on this host needs none of this and joins the `CONNECT` allowlist instead. Both shapes are declared, because they are different boundaries: the allowlisted-remote shape adds one more `CONNECT` target, while the local-relay shape hands the contained program a channel into a host service that outlives the sandbox. That second one is a real residual and it is ranked in Section 6.

`PI_PROXY` specifically, not `PI_PROXY_<PROVIDER>`: "`PI_PROXY` is installed on the process-wide `fetch` at CLI startup, so it also covers requests made outside the provider fetch wrapper — OAuth token refresh and login, usage probes, model discovery" (`omp://environment-variables.md`). The provider-scoped form does not cover those, and a run whose OAuth refresh has no route dies mid-stream rather than at startup. The forwarder listening on loopback is the *proxy*, not the *target*, so OMP's documented bypass — "Loopback, link-local, private-range (`10/8`, `172.16/12`, `192.168/16`), and `NO_PROXY` targets always bypass, so local model servers and MCP hosts stay direct" (`omp://environment-variables.md`) — does not apply to it; the provider endpoint is a public target and is proxied.

That same bypass rule has a consequence worth stating plainly: a profile whose `baseUrl` is a loopback or private-range model server is unreachable under this backend. Such a target bypasses the proxy by design, and inside the sandbox's network namespace there is nothing on loopback but the forwarder and no route to a LAN address at all. A local-model profile therefore fails to reach a model rather than reaching one unproxied — the correct direction to fail, and a limitation rather than a defect.

**Why `network_default_deny: true` is honest here.** The declaration is about arbitrary egress, and arbitrary egress is denied by the absence of any path: no interface, no route, no resolver. The sandbox cannot resolve a hostname, so DNS is not even available as a channel. What exists instead is not a filtered route but two named sockets — the provider `CONNECT` proxy and, where the broker is local, the broker relay — each reaching exactly one host-side process that Code owns and the sandbox cannot reconfigure. Public research, the other reason an analysis worker would want the network, does not travel either: it goes through Babel's broker, a host-side control-plane surface with its own disclosure, SSRF, redirect and content-limit obligations (§14), so research requests originate from Babel on the host and never from inside the sandbox. Nothing about the design leaves a general egress route that happens to be filtered; there are two endpoints reachable by construction, and everything else is unreachable because it is unreachable.

**What remains reachable, stated plainly.** The resolved provider endpoint, over `CONNECT`, to that host and port; and the run's auth broker, where it is a service on this host. TLS inside a `CONNECT` tunnel is end-to-end, so the proxy governs *where* bytes go and has no view of *what* goes — it cannot distinguish a legitimate prompt from an exfiltration payload, and should not be described as though it could. Additionally, if the provider endpoint resolves to shared or multi-tenant infrastructure, the allowlisted host name is not a single-purpose destination. And each unix socket is a live bidirectional channel from the contained program into a host process, so Code's proxy and relay implementations are host-side attack surface reachable from inside the sandbox; both are in the trust base (Section 6, item 6).

## 6. Escape assumptions: what this does not contain

Ranked by how reachable each is from inside a running sandbox, most reachable first. This list and the `escape` string Code declares are the same account at two levels of detail: the string carries the residuals a reviewer must weigh while reading a receipt, this section carries all of them with their reasoning. The string may be shorter; it may not say anything this section contradicts, and a residual discovered in one belongs in the other in the same change.

1. **Exfiltration to the provider endpoint is possible.** The permitted path carries arbitrary bytes inside an opaque TLS tunnel. Anything the worker can read — the corpus it was granted, the filesystem it was given, its own environment — it can send to the provider as prompt content, and no mechanism in this design distinguishes that from analysis. This residual is accepted rather than mitigated, because a model that cannot reach a model provider cannot analyze anything. It is the reason the allowlist is one endpoint rather than a policy: narrowing the destination set is the only lever this design has, and it has been pulled as far as it goes.
2. **The provider credential is inside the sandbox, so sandbox compromise exposes it.** OMP authenticates to the provider itself, which means the API key or OAuth token is in the sandbox's environment or configuration where the model's own `bash` can read it. The hardening that would close this is a **credential-injecting reverse proxy**: Code holds the credential host-side, terminates TLS against the model API, injects the authorization header, and configures OMP's provider with `auth: none` — a documented OMP mode ("`auth`: `apiKey` (default), `none`, or `oauth`" and "Providers marked `auth: none` are treated as available without credentials", `omp://models.md`), so it needs no OMP change either. It is deferred, not dismissed, and the reason is scope: today Code passes provider traffic through opaquely, and this would put Code on the provider protocol path — owning OAuth token refresh (which `PI_PROXY` currently carries generically, per Section 5), streaming response passthrough for every supported provider API shape, and a per-provider notion of where the credential goes. That is Code owning a moving external contract for every provider it supports, which is a larger commitment than the residual it closes, and it stays a named future change rather than a silent gap.
3. **The auth broker is reachable for the life of the run, when it is local.** Where the run's broker is a service on this host, Section 5's relay puts it on the sandbox's own loopback. A compromised worker can therefore drive the broker directly — not merely spend the credential it already holds, but ask for more, for as long as the run lasts. The relay is what makes a networkless run able to authenticate at all, so removing it is not an option while item 2 stands; the two close together, because a credential-injecting proxy would keep both the credential and the broker conversation host-side. Where the broker is remote it is one more `CONNECT` allowlist entry instead, which is the weaker residual of the two shapes.
4. **Isolation rests on unprivileged user namespaces, so a kernel userns escape defeats it.** Every namespace in this backend is created by an unprivileged process through `CLONE_NEWUSER`. That surface has produced privilege-escalation vulnerabilities repeatedly, and this design has no second layer behind it: a kernel bug in namespace handling is a complete escape, not a degraded boundary. The mitigation is a hypervisor, not a flag — see Section 7's first Darwin path, which is the same idea.
5. **No seccomp filter is applied, so the full syscall surface is reachable.** `bwrap` can install one (`--seccomp`) and this backend does not. Every syscall the host kernel offers is callable from inside, which both widens the kernel attack surface behind item 4 and means containment is entirely namespace- and cgroup-based with no syscall-level defense in depth. This is a deliberate present state and not an oversight: a filter is only worth declaring once its allowlist has been derived from what OMP actually needs, and a filter that breaks the worker in an unrelated release is worse than none. Adding one invalidates this document (Section 8).
6. **The trust base is host-side and unaudited by this design.** The host kernel, the `bwrap` and `systemd` binaries, the Code process that composes them, and Code's `CONNECT` proxy and broker relay. The two host-side sockets deserve separate mention because items 1 and 3 reach them: a parsing or target-validation bug in either is a host-side vulnerability that the contained program can reach directly.
7. **The boundary is only as narrow as the mount set Code composes.** `filesystem_isolation: true` says the worker saw a filesystem constructed mount by mount, not that any specific path was excluded. A read-write bind of the corpus is a read-write bind. So a reviewer checking a receipt against this document learns the *kind* of isolation and must read Code's backend for the *extent* of it. One measured constraint on that mount set is load-bearing enough to record here, because nothing else guards it: **the corpus must never be the working directory.** Measured 2026-08-30, OMP discovers MCP server configurations from the working-directory root even under a private `HOME` — a planted stdio server registered its tool from twelve distinct file shapes across eleven paths, including `.mcp.json`, `mcp.json`, `.omp/mcp.json`, `.claude/mcp.json`, `.vscode/mcp.json`, and `.gemini/settings.json` — and an MCP-registered tool egresses on its own, bypassing Babel's broker entirely. Discovery is strictly at that root: a config in the parent of the working directory, or one directory below it, is not read. Since §3 classifies all archive content as untrusted data, a corpus mounted at the working directory would let a malicious transcript register an unbrokered egress tool with no model cooperation at all. Binding the corpus at its own path, with the working directory a separate empty tmpfs, is what closes it.
8. **A shared kernel shares microarchitecture.** No claim is made against timing or speculative-execution side channels across the boundary, nor against covert channels between the sandbox and the host generally. Sibling processes on one kernel are not isolated in that sense, and nothing here pretends otherwise.

## 7. Darwin

Darwin gets no qualified backend, and exploration is refused there.

macOS offers one sandboxing mechanism to an unprivileged process: `sandbox-exec`, the command-line front end to Seatbelt. Its own manual page carries "The sandbox-exec command is DEPRECATED", directing developers to App Sandbox instead, and it has been deprecated across many releases; Apple has not published a replacement for sandboxing a process that is not an entitled app bundle, and the sandbox profile language it takes has never been documented for third-party use. That is the whole difficulty: the supported path is app-bundle entitlements, and an analysis worker launched by a Go program is not an entitled bundle. Two of the four required properties cannot be honestly declared over it:

- **No resource ceilings.** There is no cgroup equivalent. `setrlimit` and `taskpolicy` bound one process's own limits or scheduling class, not a process tree's aggregate memory, CPU or task count, and nothing stops a child from being outside whatever was set. `resource_ceilings: true` over that would be a false boolean.
- **No real disposability.** A Seatbelt profile filters operations by path predicate against the live filesystem; there is no mount namespace, so there is no constructed filesystem to discard. Teardown reduces to killing the process tree — which Babel already owns from outside (decision 53) and which is not the same property. `disposable: true` would mean "we killed it", not "its state ceased to exist".

So Darwin declares nothing, and per §10 — "with analysis disabled on any platform whose backend has not passed" — exploration is refused there rather than run behind a boundary that would have to be described falsely. Every other capability continues unchanged, because none of them executes a worker: `archive push`, `archive verify` and `archive fetch`, the session catalog and search, the local web surface, transcript viewing, and append-only review all run in Babel's own process on the operator's machine. A Darwin machine remains a full archival and review instance; it is not an analysis host.

Two paths could qualify it later, and each has a cost worth stating before it is chosen:

- **A Linux VM guest reusing this backend.** A Linux guest under Virtualization.framework (or Lima/UTM over it) runs the `bwrap`+scope backend unchanged, and the resulting boundary is *stronger* than Linux-native because a hypervisor sits behind item 4 of Section 6. The cost is operational and honest-declaration cost, not technical difficulty: the VM becomes a prerequisite the operator provisions and keeps current, Code must own guest lifetime and move both the corpus and the egress socket across the VM boundary (a shared directory or a vsock), and the declaration must then name the guest — a receipt saying `bwrap+systemd-scope` on a Darwin host without naming the VM would misdescribe where the analysis ran.
- **`sandbox-exec` with permanently relaxed, visible runs.** Filesystem confinement and network denial *are* expressible in a Seatbelt profile, so such a backend could honestly declare `filesystem_isolation: true` and `network_default_deny: true` while declaring `resource_ceilings: false` and `disposable: false`. The protocol already handles that: the strict requirement refuses it, `--unsandboxed` relaxes it per run, and the run is recorded as relaxed. The cost is that every Darwin receipt is permanently a relaxed receipt and Babel's default would never authorize a Darwin run without an explicit per-run override — a truthful arrangement, but a documented limitation rather than a qualified backend, and it buys a partial boundary at the price of normalizing the relaxation flag.

## 8. What would invalidate this document

Any of these changes makes this document wrong, and the change that makes it wrong is the change that updates it:

- **A different or additional backend.** Anything on Linux other than `bwrap --unshare-all --die-with-parent` inside a `systemd-run --user --scope`, and any Darwin backend at all, including either qualifying path in Section 7.
- **A change to the egress design.** A second allowlisted endpoint, a different proxy protocol, a proxy that is not host-side and Code-owned, or giving the sandbox any network interface. Section 5's argument for `network_default_deny: true` rests on the absence of a path, and it does not survive the sandbox gaining one.
- **A seccomp filter.** Adding one changes Section 6 item 5 and the `escape` string Code declares, and it introduces a new failure mode — a denied syscall the worker needs — that Section 4.3 would have to cover.
- **The provider credential moving outside the sandbox.** The credential-injecting reverse proxy in Section 6 item 2 closes that residual, which changes the ranked list and the `escape` string, and puts Code's provider-protocol ownership into the trust base in its place.
- **Mounting the corpus at the working directory.** Section 6 item 7 measures why: OMP registers MCP servers, which egress outside Babel's broker, from a configuration file at the working-directory root even under a private `HOME`. Archive content is untrusted by contract (§3), so that arrangement would let archived material register an unbrokered egress tool with no model cooperation. Any change to where the corpus is bound is a change to this document.
- **Removing or widening the broker relay.** Section 6 item 3 exists because the relay does. Making the broker reachable by a different mechanism, or leaving it reachable after the credential moves host-side, changes the ranked list.

Code's `Containment.escape` string and Section 6 are the same account at two levels of detail, and neither may contradict the other.
